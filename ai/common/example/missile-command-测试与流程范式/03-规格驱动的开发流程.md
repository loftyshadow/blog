# 03 · 规格驱动的开发流程

这是个 AI 辅助流程的示范仓库（单 commit、docs 下有完整设计稿 / user story / ADR / PR 计划），所以**规格密度远高于普通项目**。但其中的**追溯链结构**是可以按比例缩放引入的。

## 文档骨架

```
docs/
├── superpowers/specs/2026-07-24-missile-command-design.md   ← 总设计稿（带日期）
├── user-stories/
│   ├── README.md
│   └── US-01 … US-22（22 个故事，每个一文件）
└── architecture/
    ├── ADR-001-modular-core-and-extraction-plan.md          ← 架构决策记录
    └── plans/
        ├── README.md                    ← 带 Status 列的任务总表
        ├── pr-00 … pr-09               （10 份逐 PR 实施计划，均 Done）
        ├── rec-01 … rec-07             （7 份 review 后的改进计划，Ready）
        └── qa-consolidation-efficiency.md（QA 自身的优化计划）
features/*.feature        ← 27 个，对应故事的可执行验收
qa/procedures/*.qa.md     ← 42 份，对应故事的人读 QA 程序
qa/scripts/*.qa.bb        ← 38 个，对应程序的可执行版本
```

## 追溯链（每个环节都写明上下游）

```
设计稿 §5.2/§5.3
   ↓  Design 字段
US-03 aim-crosshair  （Status: done / Depends on: US-02）
   ↓  同名
features/aim-crosshair.feature      → 生成的验收测试
   ↓  Gherkin 字段
qa/procedures/aim-crosshair.qa.md   （Task / Suite / Gherkin 三个字段回指）
   ↓  同名
qa/scripts/aim-crosshair.qa.bb
```

一个 User Story 的实际长度（US-03 全文约 25 行）：

```markdown
# US-03 — Aim the crosshair
**Status:** done   **Depends on:** US-02   **Design:** §5.2, §5.3

## Story
As a player, I want to move a crosshair with the pointer,
So that I can choose where defensive missiles will explode.

## In scope
- Aim command updates crosshair position.
- Position is clamped to the current playfield.

## Acceptance criteria
- After aiming to a point inside the playfield, the crosshair is at that point.
- Aiming outside the playfield clamps to the nearest in-bounds position.
- Aiming does not change cities, batteries, ammo, or score.

## Out of scope
- Firing, rendering the crosshair in Quil (host stories), enemies.
```

**四个字段撑起整个流程**：

| 字段 | 为什么关键 |
|---|---|
| `Status` / `Depends on` | 依赖显式化 → AI 或人都能算出可并行的下一批 |
| `In scope` / `Out of scope` | **Out of scope 是防 AI 扩散的最有效栏位**。US-03 明确把"渲染 crosshair"推给宿主故事 |
| `Acceptance criteria` | 一条一条直接映射成 Gherkin scenario，不需要二次翻译 |
| `Design: §5.2` | 回指设计稿章节，改设计时能反查影响面 |

第三条 AC「aiming does not change cities, batteries, ammo, or score」值得单独点名：**显式声明"不该变的东西"**。绝大多数需求文档只写"该发生什么"，这条写了"不该发生什么"——而后者恰恰是回归 bug 的主要来源，也是 AI 改动最容易踩的地方。

## PR 计划：把重构切成可验证的片

`docs/architecture/plans/` 下每个 PR 一份计划：

```
pr-00-document-adr.md            先把决策写下来
pr-01-wave-start-in-core.md      一次搬一条不变量
pr-02-sfx-event-contract.md
pr-03-extract-bonus-cities.md    ┐
pr-04-extract-combat.md          │ 逐模块抽取，一个 PR 一个模块
pr-05-extract-shell.md           ┘
pr-06-core-testing-api.md
pr-07-host-input-split.md
pr-08-seedable-sky-rng.md        随机源可注入 → 为属性测试和确定性 QA 铺路
pr-09-arch-docs-invariants.md    最后把不变量写进文档与检查
```

`plans/README.md` 是一张**带 Status 列的任务总表**，分三档：主线 PR（0–9，全部 Done，Status 里写清"Done (QA merged)"还是"Done (docs landed)"）、post-review 改进（R1–R7，Ready）、QA 自身优化（Q1）。顶部一句规矩：

> Hand off **one task at a time** — 上一个任务的完整流水线跑完前不开下一个。

以及 **Rules for every PR**（五条，直接可抄）：

1. 除非计划明确要改规则，否则**行为不变**；
2. 在宿主/验收层更新完之前，**从 `core` re-export**（保持旧入口可用，避免一次性大爆炸）；
3. `bb script/arch_check.bb` 绿；
4. 单测绿 + **被触及特性的验收**绿（不要求全量验收绿，只要求你碰到的那部分）；
5. 本任务链路跑完前不开下一个计划（除非用户明确覆盖）。

第 2 条和第 4 条是重构类工作最实用的两条：**旧入口先留着**、**验收只卡你碰过的**。

配套关系：**每个抽取 PR 都有一个同名 QA 脚本守着**（`extract-combat.qa.bb`、`extract-shell.qa.bb`、`host-input-split.qa.bb`…），而 `qa/README.md` 里说明这些"迁移期脚本"何时可以退役（不变量搬进 `arch-check` 后，同一次改动里摘掉）。

**这是重构该有的样子**：不变量先被脚本钉住 → 再动代码 → 不变量搬进永久检查 → 临时脚本退役。

## 与 AI 协作的适配点

这套结构对 AI 辅助开发特别友好，原因很具体：

1. **每个 story 是一个可独立完成、可独立验证的上下文单元**——不超过一屏，AI 不需要读全仓库就能开工。
2. **AC 直接生成 Gherkin**，Gherkin 直接生成测试代码 → AI 写的实现有客观红绿信号，不靠"看起来对"。
3. **Out of scope 明写**，压住 AI 顺手改一堆无关文件的倾向。
4. **架构检查脚本**是 AI 违规时最快的反馈——比 review 时人眼发现"核心域怎么 import 了 IO"快得多。
5. **变异测试**是对 AI 写的测试的怀疑机制：AI 很擅长写出"跑得过但不断言什么"的测试，变异测试专治这个。

## 按比例缩放（真实项目怎么用）

不要照搬 23 个 story + 42 份 QA 程序。建议的最小可用版：

| 保留 | 理由 |
|---|---|
| ✅ Story 的四字段结构（尤其 Out of scope + "不该变"的 AC） | 零成本，收益立刻 |
| ✅ ADR（每个重要决策一份，带日期和上下文） | 半年后有人问"为什么这么设计"时唯一的答案来源 |
| ✅ 重构类工作的 PR 计划切片 | 大重构失败通常败在没切片 |
| ⚠️ Gherkin 全链路生成 | 需要工具链投入，仅对**验收标准复杂且稳定**的域（如财务对账）值得 |
| ⚠️ 每特性一份 QA 程序文档 | 只对**难自动化**的部分写（GUI、多宿主、跨系统链路） |
| ❌ 全部特性都走六层 | 示范仓库的密度，不是生产项目的性价比点 |
