# Missile Command：AI 辅助工程的测试与流程范式

> 参考源：Uncle Bob 的 Clojure/ClojureScript 版 Missile Command（AI 辅助流程示范仓库，单 commit，docs 下带完整 user story / ADR / PR 计划，规格密度远高于普通项目）。
> 本目录是**提炼后的可借鉴清单**，不是该仓库的说明书。语言细节（Clojure/babashka）已剥离，只留可迁移的做法。

## 一句话概括

它没有把"测试质量"寄托在"多写点单测"上，而是把**六层互相独立、且互相验证**的关卡全部挂到统一任务入口（`bb.edn`）上：
每一层的产出都被下一层怀疑一次，专治**"测试存在但无效"**（假绿）。

## 六层关卡全景

| 层 | 入口 | 规模 | 它防的是什么 |
|---|---|---|---|
| 1 单元测试 + 结构检查 | `bb test` | 41 spec 文件 / 400 个 `it` | 测试文件写了但没被跑到 |
| 2 验收测试（Gherkin→IR→生成代码） | `bb accept` | 27 feature / 187 scenario | 场景绿灯但断言其实没执行 |
| 3 变异测试（测试的测试） | `bb mutate` / `bb accept-mutate` | 逐 form 增量 + 逐 feature | 单测/验收用例没有约束力 |
| 4 属性测试 | `bb property` | 16 文件 / 164 `defspec` | 只测了想得到的样例 |
| 5 架构边界检查 | `bb arch-check` | 脚本枚举禁止依赖 | 可测性靠约定，随时间腐化 |
| 6 端到端 QA（可执行手工脚本） | `bb qa-suite` | 42 份程序文档 / 38 个脚本 | GUI/难测对象无人守 |

另有三把尺子：`bb crap`（覆盖率 × 复杂度）、`bb dry`（源码结构性重复）、`bb gherkin-ir-dry-checker`（验收 IR 层查重）。前两者都**显式列出 26 条受检模块清单**，GUI 宿主模块明确排除——不追求"全仓库 100%"这种自欺数字。

## 三个真正值得抄的点

1. **每一层验证上一层。** 单测被变异测试验证，验收用例被 Gherkin 变异验证，测试目录结构被 structure-check 验证，step 注册表被 registry-health 验证。这条链的目标不是"覆盖率高"，是"覆盖是真的"。
2. **手工 QA 文档与自动脚本一一配对**，且 `qa/README.md` 写明每个脚本的**覆盖归属**（谁负责 banner、谁负责 sound、迁移期脚本何时退役），避免重复覆盖和覆盖空洞。
3. **GUI/游戏这类难测对象**靠"**场景注入 + 事件脚本 + 行式遥测**"三件套变成可断言黑盒，而不是截图比对，也不碰私有 API。

## 使用建议（不要整套照搬）

这是示范仓库，规格密度是刻意拉满的。对真实项目，按投入产出排序引入：

1. **先上第 5 层（架构边界检查）**——最便宜，一个脚本，立刻锁死"可测性"不再腐化。
2. **再上第 6 层的"契约"部分**——给难测模块留稳定的注入 + 遥测口子，比补一堆 mock 单测值钱。
3. **再上第 1 层的结构检查 + 第 2 层的 registry-health**——低成本消灭假绿。
4. **变异测试放最后，且只对核心域跑增量**（见 01 文档里的"增量清单内嵌"手法），全量变异测试成本极高。
