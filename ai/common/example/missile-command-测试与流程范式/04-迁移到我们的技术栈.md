# 04 · 迁移到我们的技术栈

把六层关卡翻译成 Go / Java / 前端的对应物，并给一个按性价比排序的落地顺序。

## 对应物速查

| 层 | 原仓库 | Go | Java | 前端 (TS) |
|---|---|---|---|---|
| 1 结构检查 | speclj-structure-check | 校验用例数基线 / `go test -list` | Surefire 执行数断言，禁裸 `@Disabled` | Vitest `include` glob 与文件数比对 |
| 1 单测 | Speclj | `go test` | JUnit 5 | Vitest |
| 2 验收 | Gherkin→IR→生成 | godog + step 自查脚本 | Cucumber-JVM + `--dry-run` 检查 | Cucumber-js / 自定义 DSL |
| 2 registry-health | 重复/未实现/歧义 step | 扫 feature × 已注册正则做三查 | Cucumber `--dry-run` + undefined/ambiguous 断言 | 同左 |
| 3 变异 | clj-mutate（form 级增量） | `gremlins` / `go-mutesting` | **PIT**（history 增量，最成熟） | Stryker（`incremental: true`） |
| 4 属性 | test.check | `pgregory.net/rapid` | jqwik | fast-check |

## 落地顺序（按性价比）

### 第一步：架构边界检查（1 天，收益立刻）

最便宜的一层，而且**它保护的是所有其他层的前提**——核心域一旦耦合 IO，后面全部退化成集成测试。

写清楚三类禁令，照原仓库的分层：

1. **纯核心禁止依赖**：IO、框架、HTTP、ORM、宿主/驱动层。
2. **测试适配层只许用公共 API**，不许碰被测模块的内部结构（原仓库禁验收层 require `world`，这条常被忽略但很关键——否则验收测试会跟着重构一起坏）。
3. **生产代码禁止依赖测试专用包**（原仓库禁生产宿主 require `missile-command.testing`）。

补一手原仓库的细节：**不止查 import，还按正则扫源码文本**，堵住反射/动态调用绕过的路子。

挂 CI，红了就是红了。

### 第二步：给难测模块建可观测契约（1–2 周）

见 [02](02-难测系统的可观测契约.md)。三个问题：能否任意摆状态？能否确定性驱动？能否不读库就断言？

对我们的场景优先做：
- **财务对账链路**：已有 ACPT 假数据命名空间，缺的是"事件脚本 + 行式遥测"。每步输出 `qa-fact type=X count=N`，脚本 grep 断言，比查 PG 稳。
- **portal / wujie 子应用**：已有 CDP + playwright-core 驱动经验，补上 `console.log("qa-sim k=v")` 遥测口子，把"截图看一眼"换成可断言。

### 第三步：消灭假绿（几天）

1. **测试执行数基线**：CI 断言实际执行用例数不低于上次，防静默跳过。
2. **验收 step 三查**（如果用 BDD）：重复 / 未实现 / 歧义。
3. **把 README 里的规则变成断言**——原仓库那句「生成产物不入库」是被 spec 守着的。我们仓库里同类候选：分支/提交规范、权限码三处同步、导出档位互斥、菜单 route-meta 每叶一码。凡是 CLAUDE.md 或 wiki 里写着"必须…"的，都问一句"它有断言吗"。

### 第四步：变异测试（只对核心域，增量跑）

不要全仓库跑。选**规则密集、bug 代价高**的包：金额计算、对账撮合、权限判定、状态机。

- Java：PIT + `historyInputFile`，`targetClasses` 限定。
- Go：`gremlins` 限定包。
- 借鉴「清单跟着代码走」：把上次验证结果存成 sidecar（`pkg/xxx/.mutation.json`）并入库，改代码 → hash 变 → 只重跑变的部分。

### 第五步（可选）：属性测试

对**有代数性质**的东西才值得：金额拆分求和守恒、对账双向平衡、排序/分页幂等、序列化往返。**独立 task 跑，不计入覆盖率门槛**。

## 三条一开始就要立的规矩

1. **受检清单显式化。** 不写"全仓库覆盖率 80%"，写"这 27 个模块受检，宿主/胶水层不受检"。诚实的小数字 > 含水的大数字。
2. **测试资产有退役规则。** 迁移期脚本、临时守卫，在不变量搬进永久检查的**同一次改动里**摘掉。没有退役规则的测试套件三年后没人敢删也没人敢信。
3. **覆盖归属写下来。** 谁负责哪块，一份表。防的是重复覆盖（浪费）和覆盖空洞（以为有人管，其实没有）。
4. **手工用例与自动脚本同名配对。** 别把手工用例放 Excel/Wiki——同目录同名，自动化缺口就能一条命令枚举出来，自动化率从"拍脑袋"变成"可计算"。
5. **重构 PR 只卡碰过的那部分验收**（原仓库 PR 规则第 4 条），并且**旧入口先 re-export 留着**（第 2 条）。这两条是大重构能切片推进的关键，否则每个 PR 都要背全量绿灯，最后只能攒成一个巨型 PR。

## 一句话总结

这个仓库真正的洞见不是"测试要多"，是：

> **每一层测试都可能是假的，所以每一层都需要另一层来怀疑它。**

架构检查怀疑"可测性"，结构检查怀疑"测试被执行"，registry-health 怀疑"断言被执行"，变异测试怀疑"断言有约束力"，对照组用例怀疑"实现不是常量返回"，文档抽取怀疑"文档还活着"。
