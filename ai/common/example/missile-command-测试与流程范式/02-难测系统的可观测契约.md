# 02 · 难测系统的可观测契约

GUI、游戏、实时渲染、桌面/浏览器双宿主——这类东西的常规解法是截图比对（脆、慢、噪音大）或直接放弃 E2E。这个仓库的解法是：**给被测对象设计一套稳定的、公开的、面向 QA 的接口**，把它变成可断言黑盒。

三件套：**场景注入 + 事件脚本 + 行式遥测**。

---

## 一、QA CLI 面（公开的、文档化的）

游戏本体留了一组 CLI 参数，写在 README 的 `### QA mode (CLI affordances)` 章节里，属于**已发布的开发者接口**：

| 参数 | 作用 |
|---|---|
| `--qa-scenario <file.edn>` | **场景注入**：用 EDN 直接摆棋盘（当前屏幕、敌方导弹的起点/目标、城市状态…） |
| `--qa-events <file.txt>` | **事件脚本**：定时输入序列，一行一条（`wait 2.0` / `start` / `key 1` / `enemy battery:left` / `quit`） |
| `--qa-speed 10` | **加速模拟**：5.7 秒的导弹飞行 0.6 秒跑完 |
| `--no-keyfocus` | 不抢键盘焦点（macOS 下设 `apple.awt.UIElement`），可后台跑 |
| `--qa-telemetry` / `--qa` | 打开遥测输出 |
| `--qa-fireball 217,40,50` | 精确注入一个火球，用于构造拦截/不拦截两种对照 |

关键：**这些是产品的一部分，不是测试后门。** 有文档、有稳定语义，所以脚本依赖它们不算耦合内部实现。

## 二、行式遥测（stdout 的 key=value）

游戏用 `key=value` 行式协议打到 stdout：

```
qa-sim  cities_alive=5 battery_left_destroyed=true last_enemy_fate=fireball ...
qa-fire battery=none ...
qa-sfx  ...
```

脚本按前缀过滤行、按 `key=` 正则取值即可断言：

```clojure
(defn field  [line key] (second (re-find (re-pattern (str key "=([^\\s]+)")) line)))
(defn sims   [out] (lines-starting "qa-sim " out))
```

**为什么是 key=value 而不是 JSON**：单行、可 grep、人眼可读、增量加字段不破坏老断言。对"边跑边输出"的实时系统，行协议比结构化文档友好得多。

## 三、断言长这样

一个真实用例（`enemy-missiles-impacts.qa.bb`，A–D 四段）：

```clojure
;; B: 城市被击中 → 存活数掉到 5
(let [r   (launch! {:scenario {:screen :playing :enemies [{:target [:city 0]}]}})
      hit (first (filter #(= 5 (long-field % "cities_alive")) (:sims r)))]
  (assert! hit "city 0 should die -> 5 alive"))

;; C: 路径上放火球 → 拦截成功，城市仍活着
(let [r (launch! {:scenario {:screen :playing
                             :enemies [{:origin [217 0] :target [:city 1]}]}
                  :extra  "--qa-fireball 217,40,50"
                  :events ["wait 1.5"]})
      fate (first (filter #(re-find #"last_enemy_fate=fireball" %) (:sims r)))]
  (assert! fate "expected fireball fate")
  (assert! (= 6 (long-field fate "cities_alive")) "city alive at intercept"))

;; D: 火球放远 → 不拦截（对照组）
```

注意 **C/D 成对出现**：正例 + 对照组。只写 C 的话，"永远返回拦截成功"的实现也能过。

脚本里甚至有注释记下踩过的坑：

> `Title freezes combat; start wipes staged scenario entities.`
> `Static fireball TTL≈1s — place near sky so the enemy enters it promptly.`

这些是把 GUI 变成可断言接口时真实的时序陷阱，写在脚本里比写在 wiki 里活得久。

## 四、文档即接口（最反直觉的一招）

QA 脚本**不硬编码测试命令**，而是**从 README 里正则抽取**：

```clojure
(defn discover-unit-command [doc]
  (re-find #"(?ms)^### Unit tests\s*```sh\s*\n([^\n`]+)\n```" doc))
```

并断言：

```clojure
(assert! (seq unit-cmd)   "README does not document a unit-test command")
(assert! (re-find #"(?m)--qa-enemy" readme)     "README missing --qa-enemy")
(assert! (re-find #"(?m)enemy_missiles=" readme) "README missing enemy telemetry")
```

**效果**：README 与真实命令、真实 CLI 参数、真实遥测字段**脱节即红灯**。文档不再是"写完就腐烂"的附属品，而是被测试守住的契约。

QA 程序文档里还明确写了 **UI Event Boundary**：

> 自动化部分必须：从用户可见的项目文档发现测试命令；从项目根目录以 shell 调用；**仅**凭进程退出码与命令输出判断成败；**不得**调用项目命名空间、core API、step handler 或测试 helper 来替代文档命令。
> 手工部分必须：用文档化的启动命令启动 app；在用户界面层交互（鼠标或 `--qa-events`）。

这条边界让"可执行 QA"不会退化成"又一套白盒集成测试"。

## 五、覆盖归属：防重叠、防空洞

`qa/README.md` 明写每个脚本负责什么，例如：

- `wave-banner` 负责 banner 文案、阶段、移动、banner 期间战斗冻结、恢复到下一波；
- `sequential-attacks-banner` 负责 banner 之前的攻击排序与特殊威胁调度；
- `wave-start-in-core` 负责"由 core 发起波次攻击"这条架构不变量；
- `sound-events` 负责游戏内音效发射时机；`sfx-event-contract` 负责静态 SFX 契约形状与宿主光标/静音行为。

还有**退役规则**：迁移期脚本（`extract-shell`、`extract-combat`、`host-input-split` 等）保留是因为它们守着当前架构边界；

> 「如果某条不变量搬进了 `bb arch-check`，就在同一次改动里从 `run-suite.bb` 摘掉对应脚本。」

这是我见过写得最清楚的**测试资产生命周期规则**——测试也会过期，得有人负责删。

### 42 vs 38：缺口是显式可见的

QA 程序文档 42 份，可执行脚本 38 个。差的 4 个特性是：`bombers-and-satellites`、`bonus-cities`、`mirv-warheads`、`smart-bombs`——都有人读的测试程序，还没有自动执行版。

**这个不对称本身是个好设计**：程序文档先行、脚本后补，缺口靠"同名文件是否存在"一眼可查（一条 `for f in qa/procedures/*.qa.md; do [ -f qa/scripts/$(basename $f .qa.md).qa.bb ] || echo MISSING; done` 就能列出来）。对比常见做法——手工用例躺在 Excel/Wiki 里，自动化率是拍脑袋估的——这里的自动化率是**可计算的**。

值得抄：**手工与自动用同名同目录结构配对**，缺口即刻可枚举，还能顺手做成 CI 里的一条警告（不是错误）。

## 六、迁移到我们的场景

| 被测对象 | 场景注入 | 事件脚本 | 遥测 |
|---|---|---|---|
| Go 后端服务 | 启动参数指定 seed 数据集 / fixture | 顺序请求脚本（HTTP/MQ 消息序列） | 结构化日志固定字段，或专用 `X-Debug-Trace` 响应头 |
| 前端（wujie 子应用等） | URL query 注入 mock 场景 | Playwright 脚本 / `--qa-events` 同构的 step 文件 | `console.log("qa-sim k=v")` + CDP 抓取，比截图比对稳得多 |
| 财务对账链路 | ACPT 命名空间假数据（已有做法） | 定序任务触发 | 每步落"事实 → 案例"计数的行式输出 |

**落地时先问三个问题**：
1. 我能不能**不启动完整依赖**就把系统摆到任意中间状态？（→ 场景注入）
2. 我能不能**确定性地**驱动一串用户级操作？（→ 事件脚本 + 时间加速）
3. 我能不能**不读数据库、不调内部函数**就判断结果对不对？（→ 遥测）

三个都"能"，这个系统就是可断言的；有一个"不能"，先补那一个，别急着写 E2E。
