# 01 · 六层测试关卡

核心思路：**每层的产出，都被另一层独立怀疑一次。** 下面逐层给出「它做了什么 → 它防的是什么 → 在别的技术栈里等价物是什么」。

---

## 1. 单元测试 + 结构检查

**做法**：`bb test` 不是直接跑测试，而是**先跑结构检查再跑测试**：

```
bb test = clojure -M:check spec   （speclj-structure-check，验证 spec 目录/命名结构合规）
        + clojure -M:test         （41 个 spec 文件 / 400 个 it）
```

结构不合格 → **直接失败**，不进入测试阶段。

**防的是**：测试文件放错目录、命名不符合发现规则，导致 runner 根本没加载它——测试写了但从没跑过，是最隐蔽的假绿。

**等价物**：
- Go：CI 里校验 `_test.go` 与被测包同包、`TestXxx` 命名；或断言 `go test ./... -list '.*'` 列出的用例数不低于基线。
- Java：断言 Surefire 实际执行的用例数 ≥ 阈值，防 `@Disabled`/命名不匹配静默跳过。
- 前端：Vitest `include` glob 与实际文件数比对。

> 关键不在工具，在于**"测试被执行"这件事本身也要有断言**。

---

## 2. 验收测试：Gherkin → IR → 生成代码

**流水线**（APS，Acceptance-Pipeline-Specification）：

```
features/*.feature (27 个 / 187 scenario)
  → gherkin-parser        → build/acceptance/ir/*.json   （中间表示 IR）
  → check-acceptance-registry                            （★ 关键关卡）
  → bin/acceptance-entrypoint-generator                  → acceptance/generated/*_test.clj
  → cognitect test-runner                                （bb accept）
```

**★ registry-health（`src/missile_command/acceptance/registry_health.clj`）** 检查三件事：

| 检查 | 含义 |
|---|---|
| `duplicate-patterns` | step 注册表里有重复 pattern |
| `unsupported-steps` | feature 里写了、但没有任何实现的 step |
| `ambiguous-steps` | 同一句话被多个 handler 命中 |

任一命中即 fail，**在生成代码之前**拦住。

**防的是**：验收测试最典型的假绿——step 没实现却被宽松匹配吞掉、或多个 handler 命中导致跑的不是你以为的那个断言。

**另一条政策**：生成产物 `acceptance/generated/` 不入库，并且有一个 spec（`generated_artifacts_spec.clj`）**强制这条政策**——即"生成物不许提交"本身是被测试守的规则，不是 README 里的口头约定。

**等价物**：
- Go：Cucumber/godog + 一个自查脚本，扫 feature 中所有 step 与已注册正则做 全匹配/重复/歧义 三查。
- 任何栈：**约定 → 脚本 → 挂 CI**。凡是写进 README 的规则，都可以问一句"它有断言吗"。

## 3. 变异测试：测试的测试

两条线：

### 3.1 源码变异 `bb mutate <file>`
用 `clj-mutate` 修改源码，看单测能否**杀死**变异体。

**最值得抄的一点：增量清单内嵌在源文件里。** 每个 `.cljc` 底部有一行 EDN：

```clojure
;; clj-mutate-manifest-begin
;; {:version 1, :tested-at "2026-07-24T14:40:19...", :module-hash "1215470259",
;;  :forms [{:id "defn/with-multiplier", :kind "defn", :line 12, :end-line 15, :hash "30054051"} ...]}
;; clj-mutate-manifest-end
```

记录**每个 form 的 hash 和上次验证时间** → 下次只重跑改动过的 form。变异测试最大的问题是慢，这一手把它变成可日常运行的增量任务，而且清单跟着代码走（改代码就一定改 hash，不会漂移）。

### 3.2 验收变异 `bb accept-mutate`
`gherkin-mutator` 对**每一个 feature 文件**做 soft 级变异（4 worker 并行），验证的是"**验收用例本身是否真有约束力**"——改了场景描述/数据，测试应该红。

**等价物**：
- Java：PIT（`pitest`），配 `historyInputFile`/`historyOutputFile` 做增量；或 `--targetClasses` 只对核心域跑。
- Go：`go-mutesting` / `gremlins`，同样只对核心业务包跑。
- 前端：Stryker，配 `incremental: true`。
- 「清单内嵌源文件」这一手在别的语言里可退化为 sidecar 文件 `foo.mutation.json`，效果次一档但仍可用。

## 4. 属性测试（与单测/覆盖率分开跑）

`bb property` → `test-property/` 16 个文件 / 164 个 `defspec`（test.check）。

**关键设计：和单测、覆盖率分开跑。** 理由是生成式测试会**污染覆盖率数字**——随机输入偶然走到的分支，会让覆盖率看起来比真实的确定性保障高。

**等价物**：Go 的 `testing/quick` 或 `rapid`、Java 的 jqwik、前端的 fast-check。都建议**独立 task、不计入覆盖率门槛**。

---

## 5. 架构边界检查（可测性锁死）

`script/arch_check.bb` 用脚本枚举禁止依赖，而不是靠约定：

| 层 | 禁止 require |
|---|---|
| 纯核心 `.cljc`（游戏规则） | `quil.*`、`missile-command.jvm.*`、`.browser.*`、`.acceptance.*`、`clojure.java.io`、`java.io`、`java.nio`、`babashka.*` |
| 验收适配层 | `missile-command.world`（**只能用 core 公共 API，不许碰 world 内部**）、各宿主、quil |
| `jvm.input`（宿主输入映射） | 渲染 / 窗口 / 音频 / 持久化 / `java.awt` / `javax.swing` |
| 生产宿主 | `missile-command.testing`（测试专用 API 不得泄漏进生产） |
| `host_input.cljc` | 正则级别扫源码文本，禁 `js/`、`q/`、`quil.` 等 |

注意最后一条：不止查 require，还**按正则扫源码文本**，堵住动态调用绕过 import 检查的路子。

**防的是**：可测性靠人守 → 半年后核心域偷偷 import 了 IO，从此只能起真容器测。**这是投入产出比最高的一层**（一个脚本、零维护、立刻生效）。

**等价物**：
- Java：ArchUnit（最直接对等）。
- Go：`depguard` / `go-arch-lint`，或 20 行脚本扫 import 块。
- 前端：ESLint `import/no-restricted-paths`、dependency-cruiser。

## 6. 端到端 QA：可执行的手工测试脚本

最有意思的一层，单独展开见 [02-难测系统的可观测契约.md](02-难测系统的可观测契约.md)。要点：

- 每个特性一份 `qa/procedures/*.qa.md`（**人读的**测试程序，42 份）**配一份** `qa/scripts/*.qa.bb`（**机器执行同一程序**，38 个）。
- 程序文档里明确划**「自动化部分 / 手工部分」边界**，并规定自动化部分"只能走文档公开的命令，不许调用项目命名空间、core API、step handler 或测试 helper"。
- `bb qa-suite` 分三档：`smoke`（快速信心）/ `feature <name>`（单点调试）/ `full`（全量），全局检查（arch/property）在套件级只跑一次，脚本内的重复自检被套件跳过。
- 共享 helper 统一在 `qa/scripts/lib/common.bb`，新脚本必须复用而非复制。

## 两把辅助尺子

| 任务 | 作用 | 关键做法 |
|---|---|---|
| `bb crap` | crap4clj：覆盖率 × 复杂度，找"又复杂又没测"的函数 | **显式列出 26 个受检模块**，GUI 宿主排除 |
| `bb dry` | dry4clj：结构性重复检测（AST 级，非文本级） | 同样 26 条显式清单 |
| `bb gherkin-ir-dry-checker` | 对 Gherkin **IR** 查重复（外部 APS 工具的透传任务，本仓库只有一行调用，工具实现不在仓内） | 思路是：**在中间表示上查重，而非 feature 文本上查重**——换个措辞的重复场景骗不过它 |

**值得抄的态度**：不追求"全仓库统一门槛"，而是**明确圈定"应当被守住的核心"**，宿主/胶水层坦然排除。比一个含水量 40% 的全局覆盖率数字诚实得多。
